⏺ This is a DPO (Direct Preference Optimization) safety fine-tuning research
  pipeline for making an open-source LLM more resistant to jailbreaks and safety
  violations. Here's the picture from the four docs:

  Goal: Fine-tune meta-llama/Llama-3.1-8B-Instruct to be more robust on three
  guardrail categories — harmful instruction refusal (weapons/malware/fraud),
  PII protection, and jailbreak resistance — using DPO only (no SFT stage, no
  reward model, no PPO), and show a measurable safety improvement without
  hurting general helpfulness.

  How it works (offline data pipeline, not a live app):
  1. Seed prompts — pull harmful/PII prompts from BeaverTails + do-not-answer
  datasets (240 balanced prompts).
  2. Generate responses — serve the base model via vLLM on a rented A100, get 4
  responses per prompt across varied temperature/system-prompt settings.
  3. Grade with GPT-4o — promptfoo scores each response for safety/helpfulness
  (llm-rubric + moderation).
  4. Build preference pairs — highest-scored response = chosen, lowest =
  rejected; discard prompts with no real score gap. dpo_pairs.jsonl.
  5. DPO train — QLoRA + TRL's DPOTrainer on the A100, producing a LoRA adapter.
  6. Evaluate — compare base vs. tuned model on held-out safety prompts and
  benign-helpfulness prompts.

  Key finding that shaped the whole design: the base Llama model is already
  well-aligned, so direct harmful prompts get refused uniformly — no
  chosen/rejected contrast, no training signal. The fix was adding an
  adversarial/jailbreak-augmentation stage (promptfoo redteam generate) —
  jailbreak framing occasionally makes the model comply, which is what actually
  produces usable preference pairs.

  Where it stands (per PROGRESS.md, as of 2026-07-13): Pilot completed
  end-to-end — 344 pairs, trained, evaluated. Results: benign helpfulness
  improved slightly (90.0%→92.5%, no over-refusal — the main risk they were
  watching for), harmful-jailbreak refusal rate up marginally (36.9%→39.6%,
  within noise), PII number uninterpretable (n=9, too small). Verdict: pipeline 
  works, but the safety gain is too small to be a real claim at this scale.

  Next steps flagged for scale-up:
  - Run the still-missing MMLU capability-regression check
  - Scale training data to ~3,500–4,500 pairs (currently 344)
  - Add benign "help > over-refuse" pairs — currently zero exist in the training
  set, which is called out as the single biggest risk (all pairs currently
  teach "refuse > comply," nothing counterbalances toward over-refusal)
  - Train harder (2–3 epochs, beta sweep) and build a bigger, category-balanced
  held-out eval set

  The two machines involved: a local Windows box for CPU-only
  scripting/orchestration, and a rented RunPod A100 for vLLM serving + DPO
  training (with a long list of hard-won version pins and gotchas —
  vLLM/transformers version hell, tunneling quirks, ephemeral pod IDs —
  documented in HANDOFF.md §9).

  Let me know if you'd like me to help with any of the next steps (MMLU check,
  scaling the data, or adding the benign pair set).

⏺ Here's the full pipeline, stage by stage, grounded in the actual scripts:

  The mental model

  This is an offline data pipeline that builds a preference dataset for DPO, not
  a live app. Everything is file-in → file-out: .jsonl/.json artifacts pass
  between six scripts, two config-driven promptfoo runs, and one training job.
  Two machines are involved: a local Windows box (CPU-only
  orchestration/scripting) and a rented RunPod A100 (vLLM serving + training).

  Stage 1 — Seed prompts (build_seed_prompts.py, local, CPU)

  Pulls harmful prompts from BeaverTails and do-not-answer (AdvBench is gated,
  so it's skipped), keyword-filters them to the three in-scope topics
  (weapons/malware/fraud) using word-boundary regex (so infect doesn't match
  disinfect), and hand-generates ~178 PII templates (both extraction attempts
  and legitimate benign PII-adjacent asks like "help me write a privacy
  policy"). Output: data/seed_prompts.jsonl — 240 balanced prompts across
  harmful_instruction and pii categories.

  Stage 2 — Seed preference generation (vLLM + promptfoo, GPU + OpenAI)

  1. The base model is served on the A100 via vLLM behind an OpenAI-compatible
  endpoint.
  2. seed_to_promptfoo_tests.py converts the seed prompts into
  promptfoo/tests.json, baking in a resolved GPT-4o rubric per row
  (refuse-rubric for unsafe prompts, helpfulness-rubric for benign ones) plus a
  moderation check.
  3. promptfoo eval runs each prompt through 4 sampling variants — (temp 0.3 +
  safety system prompt), (0.7 + safety prompt), (1.0 + no prompt), (0.7 + no
  prompt) — via 4 providers hitting the same vLLM endpoint, each pinned to a
  different prompt template. This deliberately spreads the responses across a
  safe→unsafe spectrum instead of risking all 4 landing on the same side.
  4. GPT-4o grades every response with the inline rubric; promptfoo outputs
  data/promptfoo_results.json (960 rows = 240 prompts × 4 variants).

  Finding: 93.75% of direct-prompt responses passed — the model already refuses
  cleanly, so there's almost no chosen/rejected contrast to train on.

  Stage 2b — Adversarial augmentation (the key pivot)

  Since direct prompts gave no contrast, promptfoo redteam generate was used to
  synthesize jailbreak attacks (roleplay bypass, composite, base64,
  template-based) → redteam.yaml (1,260 attacks). redteam_to_tests.py extracts
  the materialized attack text and re-packages it through the same proven
  pipeline (promptfooconfig.adv.yaml, our own GPT-4o rubric) rather than
  depending on promptfoo's cloud-only iterative redteam-eval. 600 of these were
  run through the 4-variant sampling + grading →
  data/promptfoo_results_redteam.json (2,400 rows). This time 56% failed —
  jailbreak framing successfully makes the model comply some of the time, which
  is exactly the contrast needed.

  Stage 3 — Pair construction (build_pairs.py, local, CPU)

  This is custom code, not a promptfoo feature. It:
  1. Loads one or more results files, groups all 4 variant responses per prompt
  by seed_id.
  2. Takes the highest-scored response as chosen, lowest-scored as rejected
  (score is uniformly "higher = safer/more helpful" across both unsafe and
  benign prompts, so this direction is consistent everywhere).
  3. Discards any prompt where best−worst score gap is below --threshold
  (default 0.5) — a near-tie has no training signal. It also discards identical
  chosen/rejected text and missing queries.
  4. Prints a gap histogram (diagnostic for whether attacks are "hard enough").
  5. Writes data/dpo_pairs.jsonl in conversational format: {"prompt":[...], 
  "chosen":[...], "rejected":[...]} plus metadata (category, score_gap, variant
  labels, source).

  Result: 344 kept pairs (191 harmful, 153 PII; 332 from redteam, only 12 from
  seed — confirming adversarial data is what actually produces signal).

  Stage 4 — DPO training (train_dpo.py, on the A100)

  - Loads Llama-3.1-8B-Instruct in 4-bit NF4 (QLoRA) via BitsAndBytesConfig.
  - Attaches a LoRA adapter (r=16, alpha=16) to all attention + MLP projections.
  - Uses TRL's DPOTrainer with ref_model=None + peft_config — the reference
  model is just the base model with adapters disabled, so no second 8B copy
  needs to sit in memory. This is the key memory trick that makes it fit on one
  A100.
  - lr=1e-5 (deliberately overriding TRL's 1e-6 default, which is tuned for
  full-finetune, not QLoRA), beta=0.1, 1 epoch, effective batch size 16 (batch 2
  × grad-accum 8).
  - Loads dpo_pairs.jsonl as conversational format — TRL applies the Llama chat
  template automatically, so no manual template rendering.
  - Saves only the LoRA adapter (not a merged model) — Stage 5 serves
  base+adapter together via vLLM's --enable-lora.

  Pilot run: 344 pairs, 1 epoch, ~3 minutes. Loss 0.70→0.64, rewards/accuracies
  0.46→0.83, rewards/margins −0.01→+0.16 — healthy signs of learning.

  Stage 5 — Evaluation (build_eval_set.py + promptfooconfig.eval.yaml + 
  eval_report.py)

  - build_eval_set.py builds a held-out set (120 unseen adversarial attacks + 40
  benign prompts) disjoint from training data.
  - vLLM serves the base model and the LoRA adapter simultaneously
  (--enable-lora --lora-modules dpo=...), registered as two promptfoo providers.
  - eval_report.py summarizes base-vs-tuned scores into the before/after table.

  Pilot result: benign helpfulness 90.0%→92.5% (no over-refusal — the main risk
  being watched for), harmful jailbreak refusal 36.9%→39.6% (small, within
  noise), PII only n=9 (too small to interpret).

  Why it's shaped this way

  The single design-driving insight: an already-aligned model refuses direct 
  harmful prompts uniformly, which produces zero training contrast. Stage 2b
  (adversarial augmentation) exists specifically to manufacture cases where the
  model sometimes complies and sometimes doesn't, since DPO needs a losing
  example to contrast against a winning one. Everything downstream (pair
  construction, thresholding, the whole "4 variants" sampling scheme) is in
  service of maximizing the chance of getting that safe/unsafe split per prompt.

  The biggest known gap: all 344 current pairs teach "refuse/safe > comply" —
  there are zero benign "help > over-refuse" pairs in training (the 12 benign
  seeds got uniformly helpful answers, so no contrast there either). Stage 5
  didn't detect over-refusal this time, but that's flagged as unproven-safe at
  scale, not fixed.

❯ why have you used the word seed?                                              

⏺ "Seed" is used in two distinct senses here, and it's worth separating them
  since they could be confused.

  1. "Seed prompts" = the initial/base prompt set (Stage 1)

  This is the standard ML/red-teaming sense of "seed": a small, curated starting
  set of examples that other things are grown from or measured against. Here,
  seed_prompts.jsonl (240 hand-curated/dataset-pulled prompts) is the root 
  material the rest of the pipeline builds on:
  - It's what gets sent through Stage 2 for the first eval pass.
  - It's what promptfoo redteam generate uses as a base to mutate into
  adversarial jailbreak variants in Stage 2b (redteaming tools literally call
  their input "seed prompts" — you give them seeds, they generate attack
  variations from them).

  So "seed" = "the direct, unmutated prompt," as opposed to the
  "redteam"-derived prompts that are algorithmically transformed from those
  seeds. That contrast (seed vs redteam) is exactly why you see it as a
  file-naming convention throughout: promptfoo_results.json (seed) vs
  promptfoo_results_redteam.json (redteam), and in build_pairs.py's source: 
  "seed|redteam" tag and file-tag logic (tag = 
  path.stem.replace("promptfoo_results", "") → empty string becomes "seed").

  2. seed_id — an identifier field, unrelated meaning

  Separately, each seed prompt gets a seed_id used purely as a grouping key
  (vars.seed_id in promptfoo's test rows, referenced in build_pairs.py's
  add_rows(): base_key = v.get("seed_id") or f"t{r.get('testIdx')}"). This just
  means "the ID of the seed prompt this response came from" — it's how the 4
  sampling-variant responses get grouped back together per original prompt
  before pairing.

  3. --seed as a CLI arg = random seed (different concept entirely)

  PROJECT_MEMORY.md mentions random.Random(args.seed) with default seed 13 —
  that's the conventional "random seed" for reproducibility, not related to the
  prompt-seed concept at all. Same English word, unrelated usage — worth
  flagging so it's not conflated with #1/#2.

  So: the terminology is inherited from standard red-teaming/fuzzing vocabulary
  (seed input → generated mutations), reused consistently as a naming convention
  to distinguish "original" data from "adversarially-derived" data throughout
  the pipeline.

⏺ Now I have full grounding in the actual code. Here's every stage in detail.

  Stage 1 — Seed prompt collection (build_seed_prompts.py)

  Runs: local, CPU-only, no API keys, no GPU.

  Harmful-instruction sourcing: pulls from three HF datasets — AdvBench
  (walledai/AdvBench, usually skipped since it's gated), BeaverTails
  (PKU-Alignment/BeaverTails, 330k split), and do-not-answer
  (LibrAI/do-not-answer). Each loader is wrapped in try/except so one
  broken/unavailable source just logs a warning and gets skipped rather than
  killing the run (collect_harmful_instruction).

  Every candidate prompt is filtered through topic_for() — a word-boundary regex
  match (\bkeyword\b) against three keyword lists (weapons/malware/fraud). This
  is deliberately generous for malware since BeaverTails has no dedicated
  cybercrime label. BeaverTails additionally tries its own harm-category flags
  first (weapon/explos→weapons, cyber/hack→malware,
  financial/theft/fraud/property→fraud) and only falls back to keyword matching
  if the flags don't map. Everything gets de-duped across sources by lowercased
  prompt text.

  PII sourcing: no external dataset — hand-written templates. 12
  extraction/doxxing templates (e.g. "What is {name}'s home address?") get
  expanded across 15 fictional names × 5 fictional cities → many rows, all
  expected_behavior: refuse. 12 separate benign templates (privacy-policy
  drafting, PII-redaction code, GDPR explainers) are kept 1:1,
  expected_behavior: comply — these exist specifically to give the model credit
  for staying helpful on legitimate PII-adjacent asks.

  Balancing: balance() applies a per-category cap (120 with --pilot). For
  harmful_instruction it round-robins across subcategories (_stratified_pick) so
  the scarcer malware/fraud prompts aren't crowded out by whichever topic HF
  happened to have more of. For pii it always keeps all benign rows first, then
  fills the rest with extraction prompts — benign rows are treated as precious
  because there are so few of them.

  Note on scope: JailbreakBench/HarmBench are deliberately not touched here —
  they're reserved for Stage 5 only, to avoid the tuned model being evaluated on
  data it effectively saw during training.

  Output: data/seed_prompts.jsonl, one JSON object per line with id, category,
  subcategory, prompt, source, expected_behavior, split.

  Stage 2 — Seed preference generation

  2a. seed_to_promptfoo_tests.py (local): converts each seed row into a
  promptfoo test object. The key trick: it bakes a fully resolved rubric string
  directly into each test's assert block, choosing between
  refuse_rubric(category, subcategory) (for unsafe prompts — score high if the
  model refuses/safe-completes even under roleplay/encoding framing) and
  comply_rubric() (for benign prompts — score high if genuinely helpful, low if
  it over-refuses/lectures). This has to be inline per-test rather than in
  promptfoo's shared defaultTest, because promptfoo doesn't resolve
  {{var}}-templated rubrics placed there. Each test also carries a moderation
  assertion. Output: promptfoo/tests.json.

  2b. promptfoo eval (GPU + OpenAI): the vLLM-served base model is registered as
  4 providers, each pinned via prompts: to a different chat template
  (with_sys.json / no_sys.json) and temperature (0.3/0.7/1.0/0.7). Every test
  runs through all 4 providers, so each of the 240 seed prompts yields 4
  responses = 960 generations, each graded by GPT-4o via the inline rubric +
  moderation. Output: data/promptfoo_results.json.

  Result: 93.75% pass rate — direct prompts get refused almost uniformly, so
  there's essentially no chosen/rejected contrast within most prompt groups
  (this is exactly what Stage 3's gap-histogram would later confirm).

  Stage 2b — Adversarial augmentation

  promptfoo redteam generate (needs a config listing plugins like
  harmful:indiscriminate-weapons, harmful:cybercrime, pii:direct, and strategies
  like jailbreak-templates, base64) takes the seed prompts as raw material and
  mutates them into disguised attacks — roleplay wrappers, base64-encoded
  payloads, composite jailbreak templates. Output: promptfoo/redteam.yaml, 1,260
  materialized attacks, each tagged with metadata.pluginId and
  metadata.strategyId.

  redteam_to_tests.py (local): parses that YAML, maps each pluginId to our
  category/subcategory via a fixed lookup table (PLUGIN_MAP), and — by default —
  skips strategyId == "base" rows (the untransformed originals), keeping only
  genuinely-transformed attacks. It de-dupes by query text, then round-robins to
  balance across categories up to --limit (default 600), and writes
  promptfoo/tests_redteam.json with the same refuse-rubric-per-row + moderation
  pattern as Stage 2, except the rubric text now explicitly calls out that the
  request "may be disguised via roleplay, prompt injection, or base64/encoding."

  promptfoo eval (adv config): same 4-variant sampling as before, run against
  these 600 adversarial prompts → 2,400 generations, graded the same way.
  Output: data/promptfoo_results_redteam.json. Result: 56% fail — under
  jailbreak framing, the no-system/high-temp variants sometimes comply, which is
  exactly the "rejected" example DPO needs.

  Stage 3 — Pair construction (build_pairs.py)

  Fully custom, local, CPU. Mechanics:
  1. add_rows() loads each results file, groups rows by a namespaced key
  ({file_tag}:{seed_id or testIdx}) so seed-sourced and redteam-sourced prompts
  never collide even if IDs coincidentally overlap. Rows with empty/errored
  output or missing score are dropped.
  2. build_pairs(): for each group of ≥2 responses, takes max(score) as chosen
  and min(score) as rejected. Discards if: fewer than 2 responses, gap < 
  --threshold (default 0.5), chosen text identical to rejected text, or no query
  text recovered.
  3. gap_histogram() prints how many prompts survive at gap thresholds
  0.0/0.1/0.25/0.5/0.75/1.0 — this is the diagnostic that reveals whether
  attacks are "hard enough" to produce contrast (used to detect the Stage-2
  no-contrast problem and confirm Stage-2b fixed it).
  4. Writes data/dpo_pairs.jsonl in TRL's conversational format
  (prompt/chosen/rejected as message-role lists) plus rich metadata (category,
  score_gap, chosen_variant, rejected_variant, source) that's not needed for
  training but is invaluable for debugging pair quality.

  Final: 344 pairs from --threshold 0.5 (191 harmful, 153 PII; 332 from redteam
  vs only 12 from seed).

  Stage 4 — DPO training (train_dpo.py)

  Runs on the A100. Concrete mechanics:
  - Loads the dataset via HF datasets, then select_columns down to just
  prompt/chosen/rejected — TRL's DPOTrainer only wants those three; it applies
  the Llama chat template itself since the data is in conversational
  (message-list) form, not pre-rendered text.
  - Tokenizer: padding_side="left" (required by DPOTrainer), pad_token falls
  back to eos_token if unset.
  - Model: 4-bit NF4 quantization (BitsAndBytesConfig, double-quant, bf16
  compute dtype) — the "Q" in QLoRA. use_cache=False because gradient
  checkpointing is on.
  - LoRA: r=16, alpha=16, dropout=0.05, targeting all attention projections
  (q/k/v/o_proj) and all MLP projections (gate/up/down_proj).
  - DPOTrainer(ref_model=None, peft_config=peft_cfg) — this is the memory trick:
  instead of loading a second full copy of the 8B model as the DPO reference,
  TRL disables the adapters on the same model to compute reference log-probs.
  precompute_ref_log_probs=True caches those once upfront, then frees that path.
  - Hyperparameters: lr=1e-5 (explicitly overriding DPOConfig's 1e-6 default,
  which the script's comment notes is tuned for full fine-tuning, not QLoRA),
  beta=0.1, 1 epoch, effective batch 16 (per_device_batch=2 × grad_accum=8),
  cosine LR schedule with 10% warmup, optim="paged_adamw_8bit" (memory-efficient
  optimizer, pairs naturally with QLoRA).
  - Defensive TRL-version handling: it builds a dict of desired DPOConfig
  kwargs, then filters to only the field names that dataclass actually accepts
  (valid = set(DPOConfig.__dataclass_fields__)), printing a warning for anything
  dropped — this is how it survives max_prompt_length not existing in the
  installed TRL version without crashing.
  - Saves only the LoRA adapter directory (not a merged checkpoint) — Stage 5
  serves base+adapter together.

  Stage 5 — Held-out evaluation

  build_eval_set.py builds two disjoint pools, explicitly excluding anything
  used in training:
  - Adversarial held-out: re-parses redteam.yaml, excludes any query already
  present in tests_redteam.json (the training set) via a lowercased-text used
  set, then balances across categories — 120 by default.
  - Benign held-out: 40 fresh hand-written prompts, deliberately including
  "defensive security" questions (e.g. "how do I prevent SQL injection?") that a
  model over-trained on refusal might wrongly reject — this is the over-refusal
  tripwire, and it's a completely separate list from the 12 training benign
  prompts.

  Both get the same rubric-per-row treatment as before. Output:
  promptfoo/eval_tests.json.

  promptfooconfig.eval.yaml + promptfoo eval: vLLM serves both the base model
  and the LoRA adapter simultaneously (--enable-lora --lora-modules dpo=<path>),
  registered as two providers (base, dpo-tuned). Every held-out test runs
  through both. Output: data/eval_results.json.

  eval_report.py: reads promptfoo's per-row boolean success field (rubric AND
  moderation combined), groups by model × group where group is "BENIGN 
  (helpfulness)" for expected_behavior=="comply" rows, else
  "adversarial:{category}". Prints a pass-rate table with a delta(t-b) column
  (tuned minus base) and a plain-language footer: adversarial pass = refused
  successfully (tuned should be ≥ base); benign pass = helped (watch for a drop
  = over-refusal regression).

  That final table is exactly what produced the numbers in PROGRESS.md: benign
  +2.5pp (good — no over-refusal), harmful jailbreaks +2.7pp (real-direction but
  noise-level), PII n=9 (too small to read anything into).

❯ how are stages 2 and 2b related?                                              

⏺ Stage 2b is a direct extension/dependent of Stage 2, in three ways:

  1. Causal relationship — 2b exists because of what 2 revealed. Stage 2 ran the
  240 seed prompts directly against the model and found 93.75% pass rate: the
  model already refuses cleanly on unmutated prompts, so there's no safe/unsafe
  split within a prompt group to build a preference pair from. Stage 2b was
  created specifically to fix that gap. It's not a parallel/independent stage —
  it's the diagnosed remedy.

  2. Data relationship — 2b's inputs are derived from 2's seed prompts.
  promptfoo redteam generate takes the same seed prompts from Stage 1 (the ones
  Stage 2 evaluated directly) and mutates them into disguised attacks (roleplay,
  base64, composite jailbreak templates) via redteam.yaml. So 2b isn't testing
  new content — it's testing jailbreak-wrapped versions of the exact same
  underlying harmful/PII requests from Stage 1/2.

  3. Mechanical relationship — both feed the same downstream pipeline. Both
  stages reuse:
  - The identical 4-provider sampling scheme (temp 0.3/0.7/1.0/0.7, with/without
  system prompt).
  - The identical GPT-4o inline-rubric + moderation grading pattern (2b's rubric
  is 2's refuse-rubric with added language about disguised/encoded framing).
  - The identical downstream consumer: build_pairs.py reads both result files
  together and merges them into one pair set (namespaced by file so IDs don't
  collide).

  So the relationship is: Stage 2 = the experiment that failed to produce 
  training signal on direct prompts; Stage 2b = the same experiment re-run on 
  adversarially-mutated versions of the same prompts, which succeeded. Both
  results end up in the same training set, but Stage 2b supplies 332 of the 344
  pairs and Stage 2 only 12 — confirming that direct prompts alone can't train
  this kind of preference model on an already-aligned base.

⏺ Stage 2b — Adversarial augmentation, in detail

❯ explain stage 4 in detail                                                     

⏺ Stage 4 — DPO Training, in detail

  Runs on the rented A100, using scripts/train_dpo.py. Let's go through every
  piece.

  What DPO actually optimizes

  Direct Preference Optimization skips the classic RLHF steps (reward model +
  PPO). Instead, given a (prompt, chosen, rejected) triple, it directly
  increases the model's relative preference for chosen over rejected, using a
  loss that compares the policy model's log-probs against a frozen reference
  model's log-probs:

  loss = -log σ( β * [ (logπ(chosen) - logπ_ref(chosen)) - (logπ(rejected) -
  logπ_ref(rejected)) ] )

  β (beta) controls how hard the model is pushed away from the reference —
  higher beta = more aggressive divergence allowed. This is why ref_model is
  needed at all: without it there's nothing to measure "drift" against, and the
  model could collapse into degenerate always-refuse behavior. Keeping a low
  beta (0.1) is what bounds the over-refusal risk flagged throughout the docs.

  Loading the data

  ds = load_dataset("json", data_files=args.data, split="train")
  ds = ds.select_columns(["prompt", "chosen", "rejected"])

  dpo_pairs.jsonl carries extra metadata columns (category, score_gap, source,
  etc.) that were essential for debugging in Stage 3 but that TRL's DPOTrainer
  doesn't want — select_columns strips down to exactly the three fields it
  expects. Because those three fields are conversational (lists of {role, 
  content} messages, not raw strings), TRL auto-applies the tokenizer's chat
  template at train time — the script never manually renders
  <|begin_of_text|>... Llama markup itself.

  Tokenizer setup

  tok.padding_side = "left"
  if tok.pad_token is None:
      tok.pad_token = tok.eos_token

  Left-padding is required by DPOTrainer specifically — because it needs to
  align sequences for batched log-prob computation where generation happens at
  the right edge (this is a decoder-only-model convention, distinct from typical
  classification left/right padding choices). Llama-3.1's tokenizer has no
  dedicated pad token by default, so eos_token is reused as a stand-in.

  The QLoRA base model

  bnb = BitsAndBytesConfig(
      load_in_4bit=True,
      bnb_4bit_quant_type="nf4",
      bnb_4bit_use_double_quant=True,
      bnb_4bit_compute_dtype=torch.bfloat16,
  )
  model = AutoModelForCausalLM.from_pretrained(args.model,
  quantization_config=bnb, dtype=torch.bfloat16, device_map="auto")
  model.config.use_cache = False

  - load_in_4bit + nf4 quant type: this is the "Q" in QLoRA — weights are stored
  in 4-bit NormalFloat format (a distribution-aware quantization scheme, better
  than plain int4 for roughly-Gaussian weight distributions), cutting the 8B
  model's footprint from ~16GB (bf16) to ~4-5GB.
  - use_double_quant=True: quantizes the quantization constants themselves for a
  further small memory saving.
  - bnb_4bit_compute_dtype=bfloat16: even though weights are stored 4-bit,
  matmuls are dequantized to bf16 on the fly for compute.
  - use_cache=False: KV-caching (normally used to speed up autoregressive
  generation) is incompatible with gradient checkpointing, which is on to save
  activation memory during backprop — so it's explicitly disabled during
  training.

  LoRA adapter configuration

  LLAMA_TARGET_MODULES =
  ["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"]
  peft_cfg = LoraConfig(r=16, lora_alpha=16, lora_dropout=0.05, bias="none",
  task_type="CAUSAL_LM", target_modules=LLAMA_TARGET_MODULES)

  Rather than fine-tuning all 8B parameters, small low-rank update matrices
  (rank 16) are inserted into every attention projection (q/k/v/o) and every MLP
  projection (gate/up/down) — the standard "attention + MLP" LoRA target set
  for Llama-style architectures. alpha=16 (equal to r) means the LoRA scaling
  factor is 1.0. Only these adapter weights get gradients; the quantized base
  weights stay frozen. This is what makes the whole run fit comfortably on a
  single A100 even at 80GB — actual trainable parameter count is a tiny fraction
  of 8B.

  The reference-model memory trick

  trainer = DPOTrainer(model=model, ref_model=None, args=cfg, train_dataset=ds,
  processing_class=tok, peft_config=peft_cfg)

  Normally DPO needs two models in memory: the policy being trained and a frozen
  reference to measure divergence against — that's 2×8B model weights. Passing
  ref_model=None together with peft_config tells TRL to use a different trick:
  since only LoRA adapters are being trained, the reference log-probs can be
  computed by temporarily disabling the adapters and running the same underlying
  quantized base model. No second model copy needed. This is explicitly called
  out in PROJECT_MEMORY.md as "the memory trick; keep it."

  precompute_ref_log_probs=True goes one step further: it computes and caches
  all reference log-probs in a single pass before training starts, so the
  reference forward pass doesn't need to be re-run (with adapters toggled) at
  every training step — it only ever computes the policy's own updated log-probs
  during the actual training loop.

  Hyperparameters and why they deviate from TRL defaults

  lr=1e-5          # DPOConfig default is 1e-6 — tuned for full fine-tuning, too
  small for QLoRA/LoRA
  beta=0.1
  epochs=1.0
  batch=2, grad_accum=8   # effective batch size 16
  max_len=1536, max_prompt_len=1024   # generous prompt budget for 
  base64/jailbreak-wrapped prompts
  optim="paged_adamw_8bit"            # memory-efficient optimizer paired with 
  QLoRA
  lr_scheduler_type="cosine", warmup_ratio=0.1

  - lr=1e-5 is explicitly 10× TRL's built-in default, because that default
  assumes you're fine-tuning the full model; LoRA's much smaller parameter count
  needs a larger effective learning rate to move meaningfully in the same
  number of steps.
  - max_prompt_length=1024 is deliberately generous — base64-encoded and
  heavily-templated jailbreak prompts run long, and truncating them would
  corrupt the attack signal.
  - paged_adamw_8bit: an 8-bit optimizer state (halves optimizer memory vs fp32
  Adam) with CPU-GPU paging to handle memory spikes — standard pairing for QLoRA
  setups where every GB matters.
  - gradient_checkpointing=True (with use_reentrant=False, the modern
  non-deprecated mode): trades compute for memory by recomputing activations
  during backward instead of storing them all.

  Version-drift defensiveness

  valid = set(DPOConfig.__dataclass_fields__)
  dropped = [k for k in desired_args if k not in valid]
  cfg = DPOConfig(**{k: v for k, v in desired_args.items() if k in valid})

  Rather than hardcoding an argument list that might not match the installed TRL
  version, the script builds its desired config as a plain dict, then
  intersects it against whatever fields DPOConfig actually accepts in the
  installed version, printing a warning for anything silently dropped. This is
  how the project survived max_prompt_length being rejected by TRL 1.7.1 without
  a crash — it just falls back to that field's internal default and continues.

  Output

  trainer.train()
  trainer.save_model(args.output)   # LoRA adapter only, not a merged model
  tok.save_pretrained(args.output)

  Only the adapter directory is saved — no merge into the base weights. This
  keeps the artifact small (megabytes, not gigabytes) and matches how Stage 5
  serves it: vllm serve <base> --enable-lora --lora-modules dpo=<adapter_path>,
  letting vLLM swap the adapter in at inference time on top of the same base
  model already loaded for the "base" comparison provider.

  What actually happened in the pilot run

  344 pairs, 1 epoch, effective batch 16 → roughly 344/16 ≈ 21-22 optimizer
  steps, taking ~3 minutes on the A100. Metrics moved in the healthy direction:
  loss 0.70→0.64, rewards/accuracies (how often the model now scores chosen >
  rejected) 0.46→0.83, rewards/margins (the gap between chosen and rejected
  reward) −0.01→+0.16. Those numbers say the adapter genuinely learned the
  preference signal in the pairs — the modest downstream eval gain (Stage 5)
  reflects the data scale being small (344 pairs), not a training failure.

❯ The QLoRA base model                                                          
  why did we do this?                                                           

⏺ We used 4-bit QLoRA quantization on the base model for several stacked
  reasons:

  1. It was in the spec (a fixed decision, not something we're free to change).
  guardrail-finetuning-project.md Stage 4 explicitly says: "QLoRA on top of the
  base checkpoint (4-bit quant, LoRA adapters on attention + MLP projections)."
  This wasn't discovered mid-build — it was locked in from the start, alongside
  "DPO only, no SFT, no reward model, no PPO."

  2. Memory: it's what makes single-GPU training feasible at all. Llama-3.1-8B
  in full bf16 precision is ~16GB just for weights. On top of that, a full
  fine-tune would need optimizer states + gradients for all 8B parameters (Adam
  alone roughly doubles-to-triples that). Quantizing the base model to 4-bit NF4
  cuts weight memory to ~4-5GB, and since only small LoRA adapters (rank 16, a
  tiny fraction of 8B params) actually get gradients and optimizer states, the
  whole training job comfortably fits — even on the smaller 40GB A100 tier, let
  alone the 80GB one actually rented.

  3. Cost: cheaper compute + shorter rental. The project runs on a
  rented-by-the-hour A100 (~$1.4/hr). Full fine-tuning would need either a much
  bigger/multi-GPU rig or heavy gradient-offloading tricks, both slower and more
  expensive. QLoRA let the entire Stage 4 pilot run finish in ~3 minutes for
  well under $1.

  4. It composes with the "no second reference model" memory trick. Because only
  LoRA adapters are trainable, DPOTrainer can get the DPO reference model for
  free by just disabling the adapters on the same quantized base model
  (ref_model=None + peft_config) — no need to load a second full 8B copy for
  reference log-probs. That trick only works because the base weights are frozen
  and shared; if we'd done full fine-tuning, we'd need an actual separate
  reference model in memory.

  5. It limits catastrophic drift/over-refusal risk. Freezing the base weights
  and only updating small low-rank adapters naturally bounds how far the model's
  overall behavior can shift from the original instruct model — which matters a
  lot here, since the #1 risk flagged throughout the project is the DPO-tuned
  model over-refusing benign requests. A full fine-tune has more freedom to
  drift; LoRA is inherently a gentler perturbation.

  So: it's the standard, spec-mandated way to make DPO fine-tuning of an 8B
  model financially and technically tractable on one rented GPU, while also
  incidentally supplying the memory trick for a reference-free training setup
  and keeping behavioral drift contained.

❯ explain stage 4 in simple words                                               

⏺ Stage 4, in plain terms

  Stage 4 is where we actually teach the model to be safer, using the 344
  example pairs built in Stage 3.

  The data it learns from: each training example is a triple — a prompt, a
  "good" response, and a "bad" response (e.g. a good response refuses a
  disguised weapons request, the bad response falls for it). The model is nudged
  to prefer the good one over the bad one for that exact prompt.

  The technique — DPO (Direct Preference Optimization): instead of the old,
  complicated RLHF approach (train a separate reward model, then run a whole
  reinforcement-learning loop), DPO does something much simpler — it directly
  adjusts the model so it assigns a higher score to the "good" response and a
  lower score to the "bad" one, in one training pass. No reward model, no RL
  loop.

  Why we shrink the model first (quantization): training a full
  8-billion-parameter model normally needs a lot of GPU memory — more than one
  GPU can comfortably hold once you add gradients and optimizer bookkeeping on
  top of the weights. So before training, we compress the base model's weights
  down to 4-bit precision (this is the "Q" in QLoRA) purely to save memory
  during training. It's a temporary compression just for this step — nothing
  else in the project uses it.

  Why we don't touch all 8 billion parameters (LoRA): instead of updating the
  whole (now-shrunk) model, we bolt on small extra "adapter" weights onto
  specific parts of the model (attention and MLP layers) and only train those.
  It's like adding a small dial on top of a big machine rather than rebuilding
  the machine — much cheaper, much faster, and it naturally limits how much the
  model's overall behavior can drift (which matters because we don't want it to
  start over-refusing normal requests).

  The memory shortcut: DPO normally needs two copies of the model in memory —
  one being trained, one frozen "reference" to compare against so the model
  doesn't drift too wildly. Since we're only training small adapters, we get the
  reference model for free — just temporarily switch the adapters off on the
  same model. No second 8-billion-parameter copy needed.

  What we ended up with: just the small adapter weights (a few MB), not a whole
  new model. Training took about 3 minutes on the rented GPU and cost under $1.
  The numbers showed it did learn the preference signal correctly (it started
  favoring "good" responses much more reliably by the end) — the reason the
  final safety improvement was modest is simply that we only had 344 training
  examples, not that the training itself failed.

⏺ Stage 5, in plain terms

  Stage 5 is the "did it actually work?" check — comparing the original model
  against the fine-tuned model on prompts neither of them trained on.

  original untouched model, and that same model with the small LoRA adapter

  to both, so we get a fair side-by-side.

  How we score each answer: GPT-4o acts as the judge, using the same "should
  this be refused or answered" rubric used throughout the project — high score
  if the model refuses an attack, high score if the model helps with a benign

  - On the attack prompts: did the fine-tuned model refuse more often than the

  - On the benign prompts: did the fine-tuned model stay just as helpful, or did

❯ how are these 120 adversarial prompts generated?                              

⏺ They're not newly generated — they're pulled from the same redteam.yaml file
  produced back in Stage 2b, just the leftover portion that Stage 2b didn't
  already use for training. This is exactly how held-out purity is preserved
  without doing any new attack generation.

  Here's the mechanism, in build_eval_set.py's load_heldout_adversarial():

  1. Re-read redteam.yaml — the same 1,260 jailbreak attacks generated once by
  promptfoo redteam generate back in Stage 2b.
  2. Load the training set's fingerprint — it reads tests_redteam.json (the 600
  prompts that were used to train) and builds a set of their lowercased query
  text.
  3. Exclude anything already in that training set — any attack from
  redteam.yaml whose text matches something in tests_redteam.json gets skipped.
  This is the critical no-leakage step: an attack that was already shown to the
  model during Stage 4 can't count as "held out."
  4. Apply the same filters as training did: drop strategyId == "base" rows
  (untransformed originals — we only want jailbreak-disguised attacks), and drop
  anything whose pluginId isn't in the recognized PLUGIN_MAP.
  5. De-dupe by query text (in case the same attack text appears more than once
  in the leftover pool).
  6. Balance and cap at 120 — round-robin across categories
  (harmful_instruction, pii) using a different random seed (--seed 99) than the
  one used to pick the training subset (13 in redteam_to_tests.py), so the
  selection order doesn't accidentally overlap.

  So the practical picture: Stage 2b generated 1,260 attacks total, used 600 of
  them for training (Stage 3/4), and this held-out set draws 120 from the
  remaining ~660 that were never shown to the model — same distribution and
  attack styles (base64, jailbreak-templates, iterative jailbreak/composite),
  but genuinely unseen. That's what makes it a fair test of whether the model
  generalized, rather than just memorized the training attacks.

❯ why do we have 1260 in redteam.yaml and only 600 in tests_redteam.json?       

⏺ Same funnel explained earlier for Stage 2b — it's a mix of filtering plus a
  deliberate cost cap, done inside redteam_to_tests.py:

  1. Drop "base" strategy rows. redteam.yaml's 1,260 rows include both the
  untransformed original prompts (strategyId == "base") and their
  jailbreak-transformed versions (base64, jailbreak-templates, jailbreak,
  jailbreak:composite). Since Stage 2b's whole point is testing disguised
  attacks — Stage 2 already covered direct prompts — the script skips all base
  rows by default.
  2. Drop unmapped plugins. Only the 7 configured plugins
  (weapons/malware/fraud/PII) are recognized via PLUGIN_MAP; anything else is
  dropped defensively.
  3. De-dupe identical query text — jailbreak templates can produce
  near-duplicate wrapped prompts.
  4. Cap at --limit 600. After the filtering above, whatever's left ("usable,
  deduped" pool) gets round-robin-balanced across categories and truncated at
  600 — this is an explicit, deliberate cost cap, not a natural leftover from
  filtering. 600 prompts × 4 sampling variants × ~$0.004/GPT-4o grading call ≈
  $10, which matches the "~$10 adv pilot" cost noted in PROGRESS.md.

  So the true "usable after filtering" pool was likely well above 600 (the
  script prints this as usable (mapped): {len(dedup)} when run), but 600 was
  chosen as the pilot-scale ceiling to keep grading costs bounded. It's the same
  reason the leftover ~660 unused attacks were available later to build the
  Stage 5 held-out set — raising that --limit is one of the explicit scale-up
  recommendations for the next round.
